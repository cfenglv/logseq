# Logseq Self-hosted RTC 2.0.1-selfhost.3

This release hardens long-running RTC sessions, snapshot recovery, rolling upgrades, authorization, and the desktop release gate. It is backward compatible with the unversioned v1 protocol used by 2.0.1-selfhost.2 and keeps the same Sync Server URL.

## Reliability and data safety

- Reconnects automatically after sleep, standby, network changes, proxy failures, half-open WebSockets, and upload-response timeouts without requiring an application restart.
- Keeps offline edits local and resumes the same pending queue when connectivity returns.
- Retries remote transaction replay with bounded memory and capped backoff while local edits continue. Continuous editing does not become a terminal sync error, and remote transactions are never silently skipped.
- Treats server cursor regression and checksum mismatch as explicit repair-required errors instead of reporting false success.
- Preserves the current local database and client operation log before snapshot activation, restores both if activation or local transaction replay fails, and recovers safely after interruption in either the pending or committed phase.
- Uses file-level database copies in desktop and CLI runtimes, with a dedicated 128 MB release gate proving that large backups are not buffered into JavaScript memory.
- Reserves frozen snapshot metadata before streaming, expires abandoned reservations, and cleans up failed downloads without exposing a moving database view.
- Downloads graph text first and rehydrates large assets in a bounded background queue, so asset-heavy graphs do not block desktop editing or cursor progress.
- Rejects oversized WebSocket messages before sending and bounds snapshot frames, batches, logs, and frozen-snapshot retention.

## Rolling upgrades and compatibility

- Keeps the v1 WebSocket, snapshot, asset, authentication, and graph routes unchanged for existing clients.
- Adds separate v2 snapshot routes for frozen downloads and staged, atomic uploads.
- New clients negotiate v2 first and restart the complete snapshot operation on v1 when connected to an older server. They never continue a partially accepted v2 upload through v1.
- Old clients continue to use v1 against the new Worker. The Worker can therefore be deployed before or after desktop clients, although deploying the Worker first is recommended.
- Legacy v1 multipart uploads remain supported, but their unversioned wire shape has no upload identity. For data safety, an interrupted v1 upload cannot be automatically replaced; an administrator must reset that graph before retrying. Versioned v2 uploads recover automatically with a new upload ID.
- The configured Sync Server URL does not change.

## Security and lifecycle hardening

- Waits for asynchronous authorization decisions before accepting a WebSocket.
- Requires graph-owner authorization for both v1 and v2 snapshot uploads in the Cloudflare and Node adapters.
- Revokes a removed member's sockets before membership deletion and repeats revocation afterward to close the race window.
- Uses a short-lived per-socket authorization cache to reduce D1 load while preserving immediate two-phase member revocation.
- Removes an incomplete graph index entry when its initial owner-membership write fails, while still allowing the owner to recover a lost successful create response.
- Sends a bounded server error and closes failed WebSockets with code 1011 instead of leaving unusable sockets open.
- Keeps RTC status and logs to an allowlisted diagnostic shape so rejected frames and exception metadata cannot expose graph content, tokens, or arbitrary response bodies.
- Rejects Node server startup when its port is already in use, releases startup resources, and terminates upgraded sockets during shutdown.
- Narrows GitHub Actions permissions, limits Apple certificate exposure to the signing step, and gates every desktop build on RTC client/server tests, the 128 MB memory test, the production Worker build, and a Wrangler dry run.

## Upgrade notes

1. Back up important graphs and quit every Logseq process.
2. Deploy the Worker from this release using the existing Cloudflare resources and existing Worker name. Do not create a new URL.
3. Upgrade desktop clients gradually. 2.0.1-selfhost.2 clients remain supported during the rollout.
4. Confirm `/health`, open the same graph on two clients, and wait for both pending counters to reach zero before relying on the deployment.

The client remains offline-first: it does not require a permanent connection to edit. A persistent checksum, cursor, or transaction validation error is intentionally not hidden or skipped; preserve the local graph and investigate before resetting any data.

## Known limitations

- Self-hosted RTC remains experimental. Keep independent backups of important data.
- If an old v1 client is interrupted while initially uploading a graph, use the graph reset operation before retrying. The server intentionally refuses timeout-based takeover because delayed v1 chunks cannot be attributed safely.
- macOS builds without Apple Developer ID signing and notarization may still be blocked by Gatekeeper. Ad-hoc signing verifies bundle integrity but does not make other Macs trust the publisher.
- Keep official Logseq and this fork closed while using the other build because both intentionally share the `Logseq` application identity and user-data directory.

See [Self-hosted Logseq DB Sync / RTC](../selfhost-sync.md) for deployment and client configuration.
