# Logseq Self-hosted RTC 2.0.1-selfhost.4

This release strengthens RTC attachment and checksum recovery, makes the desktop release process reproducible before publication, and bootstraps in-application updates for future selfhost releases. It remains backward compatible with the v1 protocol used by earlier selfhost clients and keeps the existing Sync Server URL.

## RTC integrity and recovery

- Writes restored browser attachments as binary typed arrays, preventing LightningFS from creating a named but zero-byte file.
- Cancels queued and in-flight attachment restoration when a graph is stopped or switched and retries transient restoration failures without requiring an application restart.
- Verifies newly versioned large-title payloads against their exact SHA-256 digest before rehydration.
- Persists large-title integrity markers only for the transaction prefix that was actually uploaded and addresses snapshot markers by stable block UUID. Deferred batches and temporary entity IDs can no longer advance the local server checksum incorrectly.
- Adds a versioned server checksum while retaining the legacy checksum contract. New clients fall back when an older server omits the additive fields, and the new server omits versioned checksum data for legacy clients that did not provide a complete marker tuple.
- Expands client, Worker, and Clojure end-to-end coverage for interrupted transfers, conflicting assets, malformed metadata, cursor repair, and compatibility between old and new protocol participants.

## Desktop updates

- Fixes selfhost update discovery. `electron-updater` previously treated `2.0.1-selfhost.*` as a GitHub prerelease and then tried to match the architecture metadata channel (`latest-x64` or `latest-arm64`) against the tag channel (`selfhost`), producing `No published versions on GitHub`.
- Selfhost tags are now published as normal GitHub production releases while retaining their SemVer `-selfhost.N` version. The client uses GitHub's latest-production endpoint and then selects the correct metadata for macOS Intel, macOS Apple Silicon, Windows x64, Windows ARM64, Linux x64, or Linux ARM64.
- The updater contract is rehearsed against the real `electron-updater` GitHub provider for all six desktop targets before packaging. The test also preserves the former channel mismatch as a negative regression case.
- Update, revision, changelog, and updater-error links now point to this fork for selfhost builds instead of the upstream Logseq release page.

Versions `2.0.1-selfhost.3` and earlier must be upgraded to `.4` manually because those clients contain the broken discovery configuration. Starting with `.4`, the application can discover, download, and offer to install later production selfhost releases.

Automatic installation still depends on a supported installation format and platform trust:

- Windows should be installed with the NSIS installer.
- Linux should be run from the AppImage; archive builds are portable downloads rather than an auto-update installation.
- macOS update installation requires the current and replacement applications to use a consistent valid signing identity. Builds signed and notarized with Apple Developer ID meet this requirement. The fork's fallback ad-hoc packages are still useful for manual installation and integrity checks, but automatic replacement on another Mac is not claimed or release-gated.

## Release safety

- Adds a fast deterministic source and environment preflight and a full host-platform release rehearsal.
- Requires frozen dependency installs, RTC client/server gates, the production Worker build, Wrangler dry run, bounded-memory backup tests, Electron and CLI builds, native-module rebuilds, and packaged-runtime inspection before a commit is eligible to push.
- Rehearses the exact pushed commit on all six desktop targets and requires the successful rehearsal SHA before a beta or stable release can start.
- Validates the complete 25-file release set, updater metadata, artifact sizes, SHA-512 digests, and SHA-256 checksums before GitHub creates the release.
- Keeps selfhost releases out of GitHub's prerelease state so installed `.4+` clients can discover them through the production release endpoint.

## Compatibility and deployment

1. Back up important graphs and quit every Logseq process.
2. Deploy the Worker from this release using the existing Cloudflare resources, Worker name, and Sync Server URL. Deploying the Worker first is recommended, but older selfhost clients remain supported during the rollout.
3. Manually install `.4` on clients running `.3` or earlier.
4. Confirm `/health`, open the same graph on two clients, and wait for both pending counters to reach zero.
5. For a later `.5` release, use **Settings → General → Check for updates** to exercise the in-application update path.

The client remains offline-first. Editing does not require a permanent connection, and pending local operations remain local until connectivity returns. Persistent checksum, cursor, or transaction validation failures are surfaced rather than skipped.

## Known limitations

- Self-hosted RTC remains experimental. Keep independent backups of important data.
- Historical large-title references created before payload-digest markers remain on the legacy verification path until a new client rewrites them; this release does not retroactively authenticate those old payload bytes.
- If an old v1 client is interrupted during the initial graph upload, use the graph reset operation before retrying. Its unversioned wire format cannot safely distinguish delayed chunks from a new upload.
- macOS ad-hoc packages can still trigger Gatekeeper and Keychain trust prompts. Apple Developer ID signing and notarization are required for a frictionless distribution and a release-gated automatic replacement path.
- Keep official Logseq and this fork closed while using the other build because both intentionally share the `Logseq` application identity and user-data directory.

See [Self-hosted Logseq DB Sync / RTC](../selfhost-sync.md) for deployment and client configuration.
