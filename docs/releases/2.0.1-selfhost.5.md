# Logseq Self-hosted RTC 2.0.1-selfhost.5

This release keeps the self-hosted RTC and data compatibility contracts from `2.0.1-selfhost.4` while incorporating focused reliability fixes from the upstream Logseq DB line.

## Required manual macOS migration from `.4` to `.5`

The published `2.0.1-selfhost.4` macOS application was ad-hoc signed. Squirrel.Mac therefore tied its update requirement to that exact build's code hash, so it cannot install any different macOS build automatically. **Do not use Restart and install to move from `2.0.1-selfhost.4` to this release on macOS.**

1. Back up important graphs and quit every Logseq process.
2. Download the `2.0.1-selfhost.5` DMG for your Mac from the release page: `darwin-arm64` for Apple Silicon or `darwin-x64` for Intel.
3. Open the DMG and replace the existing Logseq application manually.
4. If Gatekeeper blocks this unnotarized build, use **System Settings → Privacy & Security → Open Anyway**. Do not change certificate Trust Settings and do not remove quarantine attributes.
5. Start Logseq and confirm the version in Settings.

This version embeds the project's fixed Ed25519 update public key. Later macOS releases use a new updater channel and a signed manifest covering the bundle ID, version, architecture, ZIP size, and SHA-512 digest. A native helper verifies that signature, the extracted App, its architecture and ad-hoc code signature, and the upgrade direction before atomically replacing the application. The private key remains outside the repository. Missing or mismatched signing material blocks the release.

The project-update private key must never be uploaded to GitHub or GitHub
Actions. CI produces unsigned macOS candidates and cannot publish a selfhost
stable, beta, or nightly release. The publisher finalizes both architecture
metadata files from the macOS login Keychain, verifies their project signatures
and the complete asset set, and only then uploads the release. This affects
only release operations; users do not provide or manage a signing key.

Project signing changes only release-artifact authentication. It does not
change graph data, local storage, Worker routes, or the RTC sync protocol;
clients from `.1` through `.4` retain their existing data, graph, and RTC sync
compatibility.

This project signature authenticates later in-app updates without changing macOS certificate Trust Settings. It is not Apple notarization. After stable `.5` is installed, the default in-app update flow automatically checks for and downloads only higher stable revisions such as `.6`; after the user clicks **Restart and install**, it verifies and installs the update automatically. Dated nightly builds use an isolated rolling GitHub prerelease and update only to later nightlies. Stable clients never discover or download a nightly, and returning from nightly to any stable release, including a higher revision, requires a manual install. Before downloading on any platform, the updater rejects mismatched tracks, release tags, versions, platforms, architectures, and installer filenames. Because these builds have no Apple Developer ID signature or notarization, every new ad-hoc application bundle may require **Open Anyway** again the first time it is opened. The updater and local ad-hoc pnpm/gulp/Electron paths never import certificates, add trust roots, or alter the user Keychain search list; an optional Developer ID workflow may import a configured certificate only into its ephemeral CI runner when Apple secrets are present. The updater never clears or removes quarantine attributes. The legacy channel remains pinned to the original `.4` metadata and payload checksum, so an un-upgraded `.4` macOS client is never offered `.5`.

## Import and settings reliability

- Preserves the empty-string title fallback when a PDF annotation has no text or matching Markdown title, instead of importing a `nil` block title.
- Repairs legacy PDF annotations created without a title during graph validation instead of deleting them, preserving their highlight data and page links.
- Treats empty or whitespace-only Electron plugin settings files as an uninitialized file and loads the plugin's declared defaults. Malformed non-empty JSON still fails explicitly.

## Encryption dialogs

- Submits the password currently visible in both E2EE password dialogs. Password-manager and autofill updates that write the input element immediately are no longer lost because of delayed renderer state updates.

## Mobile graph downloads

- Allows a remote RTC graph to start downloading from the mobile graph switcher.
- Uses native bottom sheets for download progress on native mobile and a modal dialog on mobile web, with cleanup on both success and failure.
- Keeps the graph switcher popup mounted long enough for its action to start, then closes the mobile sidebar after the action is dispatched.
- Prevents Android bottom-sheet presentation from reentering while dismissal is restoring the shared WebView. The snapshot overlay now blocks touches while visible and releases them after the final snapshot is removed.
- Always acknowledges native bottom-sheet content readiness after dismissal, including when popup state was already cleared.
- Cancels queued bottom sheets when their action is closed, so dismissed download or menu content does not reopen after the native dismissal finishes.
- Recovers from native bottom-sheet presentation, dismissal, and toolbar failures so later mobile actions can still open and close normally.

## Test harness

- Makes the CLI sync-fixture unit tests resolve helper scripts from the actual `cli-e2e` root, independent of the shell's current working directory.

## Compatibility and deployment

1. Back up important graphs and quit every Logseq process.
2. Deploy the Worker from this release using the existing Cloudflare resources, Worker name, and Sync Server URL.
3. Install `2.0.1-selfhost.5`. On macOS, manually replace `.4` as described above; Windows and Linux can continue using their normal installation paths.
4. Confirm `/health`, open the same graph on two clients, and wait for both pending counters to reach zero.

The client remains offline-first and retains the protocol compatibility of `2.0.1-selfhost.4`. Self-hosted RTC remains experimental, so keep independent backups of important data.

See [Self-hosted Logseq DB Sync / RTC](../selfhost-sync.md) for deployment and client configuration.
